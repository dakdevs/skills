The bundled inventory contains all 23 distinct `principle-` skills installed when this package was updated on 2026-10-20. The full source instructions are linked below; this table routes work and does not replace them. Preserve each skill's applicability conditions. Every inventoried skill receives both model owners even when their final finding is justified non-applicability.

At invocation, inventory `principle-` skills from the host's skill catalog and configured skill roots, including shared and agent-specific stores. Deduplicate identical copies by name and content. Use the union of installed skills and this bundled baseline so the published workflow remains self-contained; honor explicit user exclusions. An installed copy supersedes its bundled snapshot, including when they differ only in relocated links. Only divergence among installed copies without host precedence is a version conflict. Prefer the host's explicitly selected active version; if divergent versions have no defined precedence, report the conflict rather than silently merging them. Record the selected path and content hash for every skill. If no local installations are accessible, use this bundled inventory and disclose that fallback. An advertised skill whose content cannot be read is a blocker for its ownership, not permission to omit it.

For added or changed installed principles, read their full instructions, assign execution and verification obligations, and include them in the same ownership matrix. Freeze the inventory and selected contents for each task; changes require explicit inventory reconciliation and invalidate affected decisions. Never mutate the user's installed skills as a side effect of running the workflow.

## Conflicting principles

Resolve conflicts against the explicit task, repository contracts, and evidence before implementation. Redesign, deletion, structural fixes, and broad pattern inspection do not authorize unrelated cleanup or another repository. First identify the smallest complete solution; inspect other occurrences as evidence, but edit them only when required for the requested behavior. Internal API removal applies only when its stated preconditions hold; deleting a review assignment does not authorize breaking existing consumers.

Sequence work at declared verification boundaries. A planned migration can contain reversible temporary breakage inside a unit, but that unit must reach its promised checked state before dependent work advances. A deliberately failing regression baseline must fail for the expected reason; it is evidence, not a shippable result. Do not rebase user-owned work automatically merely because a copied principle mentions clean trunk; honor the selected base and repository instructions.

Use the smallest useful tool to make nontrivial work repeatable, not speculative infrastructure. A tool needed to perform or verify the requested change meets required-changes-only even if it adds no runtime behavior; commit it when the work or verification must remain rerunnable after the session. Task ledgers and temporary outputs stay outside the product checkout; that rule does not exclude necessary tools from the diff. Order verifiable commits within one draft PR unless the user or repository calls for a stack; sequencing does not itself require multiple PRs. Structural guardrails belong only where the current task demonstrates their need. Autonomy never expands authorization. Parsing belongs at an owned untrusted boundary; do not duplicate guarantees already established upstream or force TypeScript-specific mechanisms into other languages.

Each affected skill's owners must explicitly acknowledge the same resolution. The coordinator cannot hide a conflict by marking one skill inapplicable without both owners' evidence-backed agreement.
